# Retro Portal network behavior

[← README](../../README_EN.md) · [Install](INSTALL.md) · [Nginx/TLS](NGINX.md) · [Security](../../SECURITY.md)

This document describes the **actual network traffic generated by Retro Portal**. It can be shared with a hosting/CDN/provider support team when explaining the purpose of the application's connections and endpoints.

## Actual application traffic

| Endpoint / type | Purpose | Connection profile |
|---|---|---|
| `/`, `/game.html`, `/local.html` | HTML/CSS/JS UI | normal HTTPS |
| `/emulatorjs/` | EmulatorJS JS/WASM/cores | HTTPS, usually cacheable assets |
| `/roms/` | server-owned ROM delivery | HTTPS download; size varies by platform |
| `/bios/` | BIOS required by a prepared browser core | HTTPS |
| `/api/games` | public catalog | short HTTPS JSON requests |
| `/api/activity` | real online/activity data | short HTTPS JSON requests |
| `/ws/presence` | online presence and current game | long-lived WebSocket with small heartbeat/events |
| `/api/admin/*` | Library Manager | HTTPS, owner-authenticated only |

After the ROM and runtime are downloaded, emulation happens on the player's device in the browser. The server mainly serves assets and maintains web/API/presence sessions.

## WebSocket

`/ws/presence` is a real application WebSocket used for active browser-session counting, `playing`/`idle` events, the “playing now” section, and heartbeat cleanup. It does not carry ROM data and is not a generic TCP tunnel.

## What the project does not generate

A normal Retro Portal browser session does not create Xray XHTTP or arbitrary raw TCP connections. Native gRPC is not used by the current release. If a future feature genuinely uses gRPC-Web, WebTransport or WebRTC, that feature should be documented as such.

If unrelated services share the same host, use separate hostnames/paths/upstreams and describe those services accurately. Traffic not produced by Retro Portal should not be attributed to the portal.

## Typical session

1. Browser loads HTML/CSS/JS and artwork.
2. `/ws/presence` opens.
3. Starting a game downloads the required EmulatorJS runtime/core, ROM and optional BIOS.
4. Emulation runs locally in the browser.
5. The WebSocket remains active while the portal/game is open and carries small presence events.
6. Base save-state/SRAM storage stays in the browser.

For large PS1/Dreamcast images, most bandwidth is ordinary HTTPS file delivery rather than a continuous server-side stream.

## Verification

```bash
curl -i https://arcade.example.com/healthz
curl -s https://arcade.example.com/api/games | jq
curl -s https://arcade.example.com/api/activity | jq
```

The WebSocket can be tested at `wss://arcade.example.com/ws/presence` with a matching same-origin `Origin` header.

## Default production topology

```text
Internet
   ↓ HTTPS
Host Nginx / CDN
   ↓ HTTP localhost
127.0.0.1:8088
   ↓
Retro Portal web + backend
```

Keep the internal port bound to `127.0.0.1` where possible. The host reverse proxy terminates public TLS and applies external security policy.
